# Journal, 18 October 2026

## Test case 1: Semgrep invocation on an existing public Java file

**Who ran it, and where.** This run was executed by Claude (AI assistant) in a cloud Linux container, not on my own computer and not in my pinned environment. I am recording it as a reference run that shows the procedure works. It is not my own validation evidence yet. I still need to repeat it myself (see "Next").

**What was run.**
- Tool: Semgrep 1.181.0, installed with pip.
- Sample: `Md5Crypt.java` from apache/commons-codec (commit f13dd50f566c318283c4138820b15d75c26a0217, Apache License 2.0). Existing public code, not written by me, not edited.
- Rules: the 24 unmodified Java crypto audit rules in `java/lang/security/audit/crypto` from the semgrep-rules repository (commit 17e31e11ebac99fb7dfe1cd288f7a32151b6f3f9). No custom rules.
- Deviation from plan: the hosted Semgrep registry (semgrep.dev) returned HTTP 403 from the container, so the `p/cryptography` collection named in `.semgrep.yml` could not be loaded. These rules are therefore a stand-in, not the exact collection. On my own machine I must use the registry collection and record the retrieval date (ISSUE-02).

**Result.** The scan finished successfully on both runs: 24 rules, 1 file, 0 findings, parsed about 100% of the lines, exit code 0. The two runs had the same finding set (empty). Raw output: `analysis/raw/semgrep_TC1_Md5Crypt_2026-10-18.txt`.

**Pass criterion (test case 1):** a clean finish with readable output. Met in the container.

**What this does not show.** Zero findings does not mean the file has no cryptography. The file computes MD5-based password hashes, and these rules look for specific API patterns, so they may not match it. That is why test case 4 (known positive) is needed before any zero is trusted. This run also says nothing about accuracy, and it was run once in one environment, so it is not a repeatability result for my setup.
